Pyramidal Cloud-Optimized Geotiffs (POGs)

Pogs are Pyramidal COGs. COGs are Cloud-Optimized Geotiffs which are super awesome and allow for, among other things, downloading only a small subset of a huge file. A COG is still a regular GeoTIFF that any GIS can open, but its internal layout (tiling, internal overviews, header placement) is arranged so that a remote reader can grab just the tiles and zoom level it needs via HTTP range requests.

Pogs extend the concept to guarantee global pyramidal alignment: every POG covers the whole globe on one of a fixed set of supported resolutions, with a geotransform that is bit-for-bit identical across all files at that resolution. Because the grids nest exactly, any two POGs can be combined across resolutions with pure array indexing — no reprojection, no resampling, no half-pixel shifts — which is what makes fast exact zonal statistics and cross-resolution modeling in the devstack possible.

Why POGs?

  1. Solves zonal statistics inaccuracy once and for all (and is about 10-100x faster than QGIS/ArcGIS)
  2. Solves the hectare at different latitudes problem once and for all and greatly enhances accuracy (Never, never, NERVER use projected data again!)

The function for making a pog is in Hazelbean at make_path_pog. Point it at any GeoTIFF and declare what the values are:

import hazelbean as hb

# Rewrite the file in place as a POG
hb.make_path_pog('cropland_share.tif', variable_class='intensive')

# Or write to a new file and control the details
hb.make_path_pog(
    'cropland_ha.tif',
    output_raster_path='cropland_ha_pog.tif',
    variable_class='extensive',  # hectares: summed at every coarser rung
    output_data_type=None,       # optional; defaults to the input's data type (integer extensive -> Int64)
    output_arcseconds=None,      # optional; see below
    observed_area_path=None,     # 'derive' when the input's nodata means "not observed"; see below
    compression='DEFLATE',       # default
    blocksize=512,               # default
)

variable_class is one of four, and it fixes both how the overviews aggregate and how nodata is carried:

Class Examples Overviews Nodata (declared value / cells holding it)
extensive hectares, tonnes, counts sum of the children, in double precision; integer types are promoted to Int64 so the top rung cannot overflow the per-type value / none: empty cells hold 0
intensive proportions, densities, yields per ha area-weighted mean: the block sum of value × hectares divided by the block sum of hectares, written into the overview directly. intensive_weighting='none' declares the plain mean instead, a fast approximation with no exactness claim the per-type value / none: empty cells hold 0
categorical land-use classes, zone ids mode, for display only; model with per-class intensive proportion POGs the per-type value / none: empty cells hold the none class (categorical_none_value, default 0)
covariate elevation, temperature, slope unweighted mean over valid children, no exactness claim the per-type value / missing cells

The per-type value is -9999 for signed integers and floats and the type maximum for unsigned integers (255 for Byte).

An input that declares no class (no POG_VARIABLE_CLASS in its metadata, no variable_class argument) is taken as categorical if its data type is an integer and covariate otherwise, with a log line saying so. Those are the two classes that promise nothing, so a guess never manufactures an exactness claim, but declare the class: averaging hectares or summing proportions silently corrupts every coarser rung.

If the input is not already on the canonical grid, make_path_pog places it there. The steps, in order: snap the cell size to the nearest rung (or take output_arcseconds); if the input is point-registered with samples on canonical grid lines (SRTM, NASADEM, the Copernicus DEM), apply the registration shift instead of resampling (below); otherwise resample once onto the rung’s grid (a copy when already aligned; sum for extensive; nearest for categorical and integer data; bilinear for floats; the class aggregation when the target is coarser); apply any ndv_above / ndv_below censoring and value_reclassification_dict; apply the nodata rule of the class; then compute exact statistics, build the overviews by the class rule, and write through GDAL’s COG driver. If the input already validates as a POG, it does nothing.

Nodata and observed area. Every POG declares the per-type nodata value, so tools that expect a declaration (and code that copies one from a match raster) find it. In extensive, intensive and categorical POGs no cell holds it, so sums, means and zonal statistics never have to tell a missing observation from a true zero; a raster whose real values include the per-type value needs a wider type, and make_path_pog refuses it. When the input’s nodata means not observed rather than empty, pass observed_area_path='derive': make_path_pog writes <output stem>_observed_area.tif beside the output, an extensive POG of the hectares observed in each cell, derived from the nodata mask, and records it in POG_OBSERVED_AREA. An intensive raster is then weighted by the observed area rather than by ha_per_cell (POG_DENOMINATOR names it). The coverage of a zone is then itself a zonal statistic, the zone’s sum of observed area over its area. Pass a path instead of 'derive' to attach an observed-area POG you already have.

Registration shift. SRTM, NASADEM and ASTER GDEM are point-registered, with samples on whole arcseconds, half a cell off the canonical area-registered grid. Rather than resampling them, make_path_pog reads each sample as the canonical cell whose north-west corner it occupies: the geotransform moves half a cell east and half a cell south, the values are copied unchanged, the duplicated edge row and column of a 3601 × 3601 tile are dropped, and POG_REGISTRATION_SHIFT=+0.5,-0.5 is recorded. Slope, flow direction and every other derivative of the field are unchanged to the bit; the shift (15 m at 1 arcsecond) is inside the products’ own horizontal accuracy. Pass allow_registration_shift=False to resample instead.

Choosing the output resolution with output_arcseconds

make_path_pog detects the input’s resolution and snaps it to the nearest rung within a tight tolerance. The target grid is synthesized from the ladder tables (hb.write_pyramid_frame_raster, a sparse raster), so no match raster needs to exist at any rung.

That automatic detection only works when the input is already close to a rung. When it isn’t (say, 0.3-degree cells), or when you deliberately want a different rung than the input’s, pass output_arcseconds:

# An input far from any rung: choose the target explicitly
hb.make_path_pog('weird_resolution.tif', 'now_a_pog.tif', output_arcseconds=1800, variable_class='covariate')

# Deliberate cross-rung conversion: 10 s cropland hectares become 900 s cropland hectares
hb.make_path_pog('crop_ha_10sec.tif', 'crop_ha_900sec.tif', output_arcseconds=900, variable_class='extensive')

When the requested rung is coarser than the input, the conversion aggregates by the class rule. If the input sits aligned on a rung that divides the target (10 s into 900 s, say), the aggregation is exact: block sums for extensive, area-weighted block means for intensive, with nodata children left out and, under observed_area_path='derive', the observed hectares under each coarse cell carried along. Otherwise it is one GDAL resample, sum for extensive, average for intensive and covariate, mode for categorical: a single documented entry, the only resampling that product will undergo on the lattice. Without output_arcseconds, an input far from every rung raises an error that names its CRS and cell size and suggests the rung to pass.

The EE Spec convention still holds: compute in proportions or per-hectare intensities and multiply by the canonical ha_per_cell of the rung as the last step. hb.write_ha_per_cell_pog(path, arcseconds) writes that raster for any rung, and hb.ha_per_cell_rows(arcseconds, first_row, n_rows) gives the same numbers for a block of rows. It is the single definition: rows are addressed by their global index (row 0 touches 90°N), and row k’s top edge is the exact rational (324000 − k × arcseconds)/3600 degrees rounded to a double once, so a row has the same bits in a global POG, a tile, a column file or an aggregation, however the raster is split. Row areas are differences of one cumulative function at those edges, so the areas of the children of a coarse cell sum to its area, which is what makes area-weighted aggregation exact.

You can verify the result (and see exactly which criterion fails, if one does) with:

hb.is_path_pog('my_raster_pog.tif', verbose=True)

The POG spec, in summary

The pyramids paper (Colesanti Senni and Johnson, in prep.) defines the spec in full; this page is its operational summary. A POG is a GeoTIFF that passes both checks below (this is literally what hb.is_path_pog tests — is_path_global_pyramid and is_path_cog).

1. It is a global pyramid:

  • Global extent, exact geotransform. The raster spans the whole globe, (-180, res, 0, 90, 0, -res), matching the canonical geotransform for its rung bit for bit. The canonical cell size of a rung of a arcseconds is the double nearest the reduced fraction a/3600 degrees (for 300 s, the double nearest 1/12, 0.08333333333333333); a value that is merely close is a different grid. The CRS is EPSG:4326 and the file is area-registered (AREA_OR_POINT=Area or absent).

  • A rung of the ladder. The ladder has main rungs and side rungs. A main rung stands in an exact integer ratio to every other main rung, so the main set is closed under divisibility and every path of block sums between two main rungs gives the same result; successive main ratios are 3, 3, 2, 5, 3, 5, 2, 3, 2, 2, 5, 2, 3, 3, 2. A side rung is a rational cell that divides at least one main rung but not all of them; it joins the main ladder at the finest main rung it divides. Both are asserted when hazelbean is imported, and ratios are tested as reduced fractions, never as floats. Fractional rungs are named as reduced fractions, 3-10sec for 3/10 arcsecond:

    Main rungs from 1/9 s to one degree sit where WGS84 product families live: the USGS 3DEP 1/9” and 1/3” DEMs, SRTM, NASADEM, Copernicus GLO-30 and FABDEM at 1 s, 3DEP 2” (Alaska) at 2 s, ESA CCI at 10 s, WorldClim and GPW at 30 s, WorldClim 2.5’ at 150 s, MapSPAM and EarthStat at 300 s, LUH2 and GTAP-AEZ at 900 s, and the half- and one-degree climate grids. Above one degree they nest toward the 180-degree top rung, a 2 × 1 grid: the two faces of the equirectangular map. 5° is HadCRUT and NOAA GlobalTemp, 10° is the zoning and tile edge, and 30°, 90° and 180° are structural. The top rung is the aspect ratio of the map itself, so the ladder is body-independent: the one body-specific parameter is the area stack that weights aggregation. The side rungs carry the families between: 3-10 s (1/12000°: ESA WorldCover and the Lang et al. canopy height), 9-10 s (1/4000°: Hansen Global Forest Change, JRC Global Surface Water, GLAD), 3 s (the 90 m family: SRTM 3s, GLO-90, TanDEM-X 90, MERIT DEM and Hydro, HydroSHEDS, WorldPop, GHSL), 15 s (HydroSHEDS 15s, GEBCO), 180 s (CHIRPS and MODIS CMG at 0.05°), 360 s (ERA5-Land at 0.1°), 600 s (WorldClim 10’), and 9 s and 90 s, which own no product but give the 9-10 s family factor-10 steps to its join (overviews at about 280 m and 2.8 km rather than none between 28 m and 28 km). Every aligned grid has a rational cell size, so the p-q notation names every rung there could be.

  • The declared variable class and its metadata. POG_VARIABLE_CLASS is extensive, intensive, categorical or covariate; an intensive raster also declares POG_INTENSIVE_WEIGHTING (area, the default, or none) and, for area, POG_DENOMINATOR (the token ha_per_cell, or the observed-area POG). POG_OBSERVED_AREA names the companion where coverage is incomplete, and POG_REGISTRATION_SHIFT records a shift. Companion paths are stored relative to the POG’s folder.

  • The nodata convention of its class. Every POG declares the per-type nodata value (-9999 for signed integers and floats, the type maximum for unsigned integers, e.g. 255 for Byte). In extensive, intensive and categorical rasters no cell holds it; in a covariate it marks missing cells. make_path_pog converts the values, not just the declaration, and the validator checks both (the cell check reads the raster only when the value falls inside the stored exact statistics’ range).

  • Compressed with DEFLATE. This is a choice we made and in most tests deflate performs better than the more common LZW. We have also tried out ZSTD which is way better than DEFLATE but is not universally supported (yet), so a file compressed with it (or with LZW) is not a POG.

  • Internal overviews at exactly the prescribed levels, derived from the ladder rather than chosen, asymmetrically: a main-rung base carries one overview for every coarser main rung, up to the 180-degree top, and no side-rung levels; a side-rung base carries every side rung that is a multiple of it and a divisor of its join rung, then every main rung from the join up. Each overview is therefore an exact union of cells of the one before it, and only the top rung has none. The chain derivation raises on any non-integer ratio. Overviews are validated by dimensions, exactly, on read as on validation: each factor implies each overview’s size, and a missing level, an extra level or a near-miss factor all fail, since an extra level would be read as a rung that does not exist. Overhead is the sum of the squared inverse factors. The mapping is hb.pyramid_compatible_overview_levels:

  • Overviews that follow the class rule. A file records no resampling method, so is_path_pog checks the numbers: in each overview it recomputes a few cells, spread from pole to pole, from the level directly below by the declared rule, so every link of the chain is sampled. Integer levels must agree exactly and floating-point levels to a relative 1e-5 (float32 storage). Categorical and covariate POGs make no exactness claim and pass. hb.is_path_pog_overview_conformant(path, verbose=True) runs this check alone.

  • Exact statistics stored internally. Band statistics must be present and computed exactly (STATISTICS_APPROXIMATE=NO), with no stale .aux.xml sidecar shadowing them. Together with sum overviews, this makes the header of an extensive POG a source of its exact global total.

2. It is a valid COG: it passes GDAL’s COG validation — tiled layout, properly ordered internal overviews, cloud-readable header structure. The validator’s errors fail a file; its advisory warnings (e.g. “recommended to include internal overviews” on a rung with none) do not, because the exact level check above supersedes them. make_path_pog writes through the GDAL COG driver (BigTIFF, 512-pixel blocks by default) with the overviews it built and no others: left to itself the driver inserts dyadic 2, 4, 8… levels into any file that has none.

Standards

Three separate claims, each with its own evidence:

  • A POG is a valid OGC GeoTIFF and a valid OGC Cloud Optimized GeoTIFF. COG has been an OGC standard since 2023 (OGC 21-026). hb.is_path_cog runs GDAL’s validator, which implements that standard, and make_path_pog writes through GDAL’s COG driver.
  • The pyramid tiling scheme is a valid OGC Tile Matrix Set (OGC 17-083r4, “Two Dimensional Tile Matrix Set and Tile Set Metadata” 2.0). hb.get_pyramid_tile_matrix_set() publishes it: one tile matrix per rung in CRS84 with the origin at the top-left (-180, 90), id EEPyramidCRS84. It is not a quadtree — the scale progression follows the rungs, so it is not the registered WorldCRS84Quad set — which the standard explicitly allows for custom sets. Tile sizes vary by rung (below), which is why the set must be published with all twenty-five matrices (sixteen main, nine side) rather than inferred. hb.validate_tile_matrix_set_json validates the document against the schemas OGC publishes, shipped verbatim in hazelbean/ogc_schemas/tms_2.0/; that validation runs in the unit suite (test_tiles.py) and is the compliance test. hb.write_pyramid_tile_matrix_set_json(path) writes the document for use by OGC API Tiles servers or QGIS.
  • A subpog tile set is addressable through that tile matrix set. Tiles are named on disk by their south-west corner (below); hb.tile_corner_string_to_tile_matrix_index converts a corner name to the standard’s (tileMatrix, tileRow, tileCol) and hb.tile_matrix_index_to_tile_corner_string converts back. The unit suite checks the two are a bijection over every tile of a matrix.

POG, subpog, tile, tile set, VRT

Five things that are easy to conflate, defined so they stay apart:

  • POG — the global raster meeting the full spec above.
  • Subpog — a raster meeting the spec in every respect except extent. Its extent is a whole number of cells from the pyramid origin (-180, 90) at its rung (snap a box with hb.snap_bb_to_pyramid(bb, arcseconds)), and its overview levels are the global chain truncated to the levels whose cell size divides its extent (hb.get_pyramid_overview_levels_for_bb) — so every overview still lands on a rung, and the coarsest is bounded by the extent. A 1-degree tile of 1-second data therefore stops at level 3600; a 10-degree tile of 10-second data carries the chain through level 3600 (10°) and nothing coarser. Make one with hb.make_path_pog(path, expand_to_global_extent=False) (the parallel converter forwards the same flag); check with hb.is_path_subpog; a POG is a degenerate subpog. A seals AOI clip is a subpog and not a tile. The input’s footprint is snapped outward, so an input that straddles cell edges grows by up to a cell per side rather than losing data; such an extent may support no overview level at all, which is legal (the top rung has none either).
  • Tile — a subpog whose extent is exactly one cell of the published tile grid for its rung. Every tile is a subpog; most subpogs are not tiles.
  • Tile set — the tiles of one dataset at one rung and tiling, in one folder, plus the VRT that indexes them. A tile set may be sparse: tiles that would hold nothing need not exist.
  • VRT — not a raster. An XML index (gdalbuildvrt) that presents the tiles of a tile set to GDAL as one global raster: it carries the exact global geotransform, lists which tiles exist and where, and reads anything not listed as zero — what an empty cell of a POG holds — or, for a covariate tile set, as the per-type nodata. It holds no pixels, has no overviews of its own (coarse reads go to the tiles’ internal overviews), and cannot be a COG. hb.is_path_pog_tileset(vrt) checks the VRT frame is global, every source is a corner-named tile of one dataset, rung and edge covering the extent its name claims, and every tile is a subpog.

Tile and subpog naming

Corner-based, following SRTM, NASADEM, Copernicus DEM and ESA WorldCover: the south-west corner in whole degrees, latitude then longitude, each with its cardinal letter, followed by the height and width of the extent in whole degrees. The extent is in the name, so a file is interpretable without the tile matrix set, a subpog spanning several tiles is named the same way, and the same dataset may exist at more than one tiling:

lulc_esa_2020_10sec.tif                       the global POG
lulc_esa_2020_10sec_10deg/                    its tile set (folder)
lulc_esa_2020_10sec_40N_130W_10_10.tif        one tile: south-west corner 40N 130W, 10 by 10 degrees
lulc_esa_2020_10sec_10deg.vrt                 the index, beside the folder
lulc_esa_2020_10sec_20N_30E_30_60.tif         a subpog spanning 20N to 50N and 30E to 90E

Helpers: hb.get_tile_filename, hb.get_tile_filename_from_bb (names a whole-degree subpog), hb.parse_tile_filename (returns stem, rung, corner, height, width), hb.get_tile_corner_string, hb.parse_tile_corner_string, hb.get_tile_bb_from_corner_string, hb.list_tile_corner_strings. The VRT uses relative source paths, so the folder and its VRT move together. (Names of the form …_10deg_N40W130.tif, used before 2026-09-24, no longer parse.)

Products with no rung

Products delivered in a projected CRS (Sentinel-2, Landsat, NAIP and Planet in UTM; MODIS in sinusoidal; SoilGrids in Homolosine; older GHSL releases in Mollweide), products on a geographic grid that is not a rung (Copernicus Global Land Cover at 1/1008°), and products whose cells widen at high latitude (the Copernicus DEM above 50°) enter the lattice by one resample onto the rung recorded for them, so the choice is made once per product rather than once per project. The entry is a resample, never an alignment: a 10 m UTM cell is not a 3/10-arcsecond cell, and the paper’s non-nested-support treatment applies. Global POG or tile set? Support both

They solve different problems. HTTP range requests fetch only the bytes touching a window from inside one COG — exactly what COG was designed for — and work on a global POG directly, with no tiles and no VRT. So the global POG is the default form and range requests are the default subset mechanism (planned for get_path; not yet built). Tile sets earn their place where a single file is operationally impractical: 1 second and every rung finer (a global Byte raster at 1 s is over 800 GB uncompressed), datasets regenerated or checksummed piecewise, and the Drive mirror, which syncs whole files. There the VRT is the manifest telling get_path which tile files a requested box touches. Both paths converge on a future bounding-box argument to get_path; they differ only in what is fetched — byte ranges of one file, or whole tiles named in a manifest. A dataset’s entry in base_data should say which form it uses.

Round trips: hb.tile_pog_to_tileset(pog_path, tile_degrees=None) cuts a POG into a tile set (omitting tiles that hold nothing) and returns the VRT; hb.write_subpog_from_pog_window(pog_path, bb, output_path) cuts one aligned window, carrying the variable class and its metadata; any raster becomes a subpog with make_path_pog(..., expand_to_global_extent=False); a tile set becomes a global POG again by running make_path_pog on its VRT, which reads the class from the tiles and is byte-identical to the original (test_pog_spec.py checks it).

Handy extras

  • hb.make_paths_pogs_in_parallel(...) converts a list of rasters across multiple processes, forwarding variable_class, intensive_weighting, categorical_none_value, allow_registration_shift, observed_area_path='derive' and expand_to_global_extent to every file.
  • hb.write_pog_of_value_from_scratch(output_path, value, arcsecond_resolution, output_data_type, variable_class=None) and hb.write_pog_of_value_from_match(output_path, match_path, value, variable_class=None) create constant-valued POGs, useful as templates or masks.
  • hb.write_ha_per_cell_pog(output_path, arcseconds, bb=None) writes the canonical hectares-per-cell POG of any rung (extensive, Float64).
  • hb.get_pog_metadata(path) returns a file’s POG_* items (for a tile-set VRT, its first tile’s).
  • make_path_pog also accepts ndv_above / ndv_below (censor out-of-range values before the nodata rule) and value_reclassification_dict (reclassify while converting) so you can clean a raster in the same pass that pog-ifies it.
